# M7: Built-in authentication (onboarding + username/password login)

Status: approved

## 1. Intent

Hookflare 1.0.0 delegates all dashboard and admin API authentication to Cloudflare Access (DEC-5, roadmap §6.1). In practice that is the hardest step of a deployment: a fresh Worker answers `500 internal_error` ("Could not load your account") until a Zero Trust application, its AUD tag, and bootstrap emails are configured by hand. The maintainer hit exactly this on the first production deploy.

M7 replaces Access with authentication built into the Worker:

- **First visit after a deploy (no account exists):** the dashboard shows an onboarding page where the operator picks a username and password. That account becomes the first admin, and they are logged in.
- **Every later visit (at least one account exists):** the dashboard shows a login page only. Onboarding is closed for good.

Success: `pnpm run deploy -- --skip-smoke` on an empty database, open the Worker URL, create the admin, and use the dashboard — with no Zero Trust setup. The only auth configuration a first deploy needs is the setup claim protection in §6.3; Turnstile (§6.5.1) is recommended but optional.

## 2. Goals

1. Username/password login for the dashboard and admin API, with server-side sessions in D1.
2. One-time onboarding that creates the first admin, closed as soon as any loginable account exists.
3. Keep RBAC (viewer/operator/admin), audit logging, the "last active admin" guard, and the per-request `users` read exactly as they are today; only the identity source changes.
4. Admins manage other accounts (create with an initial password, reset password, change role, disable) from Settings › Users; every user can change their own password.
5. Cloudflare Turnstile protects the login and onboarding forms against bots and credential stuffing (§6.5.1).
6. Smoke tests and the bench tool authenticate with an API token (§6.9) instead of an Access service token, since they cannot solve Turnstile.

## 3. Non-goals

- SSO, OAuth/OIDC, MFA/TOTP, passkeys, email-based password reset, self-registration. (Operators who want SSO can still put Cloudflare Access in front of the Worker as a network gate; Hookflare no longer reads its JWT.)
- Keeping Access as a second auth mode. One code path only.
- Turnstile on anything other than the two public forms (login, setup).

## 4. Anti-goals (fails even if it "works")

- Anyone other than the operator can claim the first admin on a fresh deploy (see §6.3).
- Passwords or session tokens stored or logged in recoverable form.
- A deploy that leaves the admin API open, or a misconfiguration that fails open.
- Onboarding reachable again after the first account exists (including via a race of two simultaneous setup requests).
- Breaking ingress (`/in/*`) or any delivery invariant.

## 5. Constraints

- Workers runtime only: WebCrypto, no native modules. PBKDF2 in Workers is capped at 100 000 iterations.
- D1 stays the source of truth; every admin mutation and its `audit_logs` row stay in one `db.batch` (CLAUDE.md invariants).
- `ingress/` must not import from `admin/`.
- Migrations are generated by `drizzle-kit` (never hand-edited) and must pass `scripts/check-migrations.mjs`; existing `users`/`audit_logs` rows must survive.
- Tests use the `Deps` seam (`now`, `db`), no real clock.

## 6. Design

### 6.1 Identity and data model

- **Username** replaces email as the identity everywhere (`users`, `actor` in audit logs, `Me`, test deliveries, dashboard). Rule: lowercased, `^[a-z0-9][a-z0-9._@+-]{2,63}$` — `@` is allowed so existing email identities remain valid usernames after migration.
- `users`: primary key becomes `username`; add `password_hash text` (nullable) and `password_changed_at integer` (nullable). `role`, `created_at`, `updated_at`, `disabled_at` unchanged. A row with `password_hash IS NULL` cannot log in.
- `sessions` (new): `id_hash text PK` (SHA-256 of the token, hex), `username text NOT NULL` → `users.username` ON DELETE CASCADE, `created_at`, `last_seen_at`, `expires_at` (all integer ms), index on `username`.
- `audit_logs.actor_email` → `actor` (rename); same for any `*_email` actor column (`test_deliveries`). API field names follow (`actor`, not `actor_email`).
- Migration `0001_*`: existing rows keep their email as `username`; existing service identities `svc:*` are kept as disabled rows (they can never log in). One step, no expand/contract: 1.0.0 has no known installs with data, and the deploy script's restore point is the way back (my call). Schema changes come from `drizzle-kit generate`; any data step that drizzle-kit cannot express goes in a separate `drizzle-kit generate --custom` migration (allowed: it is not an edited generated file). Table rebuilds get the required `contract.json` entries. Copies must be lossless for `users`, `audit_logs`, and `test_deliveries`.
- The username rule applies to **new** usernames only. Legacy keys (long emails, `svc:*`) stay valid as path params and in lists, so `PATCH /users/:username` accepts any existing key (my call).
- `deliveries.created_by` keeps its historical values; new rows store the username. No column change (my call).

### 6.2 Passwords

- Hash: PBKDF2-HMAC-SHA256, 100 000 iterations, 16-byte random salt, 32-byte key. Stored as `pbkdf2-sha256$<iterations>$<salt b64>$<hash b64>` so iterations can rise later; verification reads the iteration count from the string.
- Comparison is constant-time.
- Policy: 12–256 characters, no composition rules; reject if equal to the username.
- A login against an unknown username still runs one PBKDF2 against a dummy hash, so timing does not reveal which usernames exist.

### 6.3 Onboarding (first admin)

- "Setup required" ⇔ no `users` row has `password_hash IS NOT NULL`. (A migrated 1.0.0 install whose users all came from Access therefore also gets onboarding once.)
- `GET /api/admin/v1/auth/state` (public) → `{ "setup_required": boolean }`.
- `POST /api/admin/v1/auth/setup` (public) with `{ username, password, setup_token }`:
  - Creates the admin with one conditional statement (`INSERT … SELECT … WHERE NOT EXISTS (SELECT 1 FROM users WHERE password_hash IS NOT NULL)`, upserting a migrated password-less row of the same username), plus its audit row (`user.onboarded`) and a session, in one batch. 0 rows inserted → `409 setup_closed`. Two racing requests cannot both win.
  - **Claim protection:** the request must carry `setup_token` equal to the `SETUP_TOKEN` Worker secret (constant-time compare). If `SETUP_TOKEN` is unset, setup returns `503 setup_token_missing` and the onboarding page explains the one command to set it. → **Open question Q1.**
- After setup succeeds the operator is logged in and `SETUP_TOKEN` is no longer used (it can be deleted).

### 6.4 Login, sessions, logout

- `POST /api/admin/v1/auth/login` `{ username, password }` → on success creates a session and sets the cookie; on any failure `401 invalid_credentials` (same body for unknown user, wrong password, disabled user, password-less user).
- Token: 32 random bytes, base64url, in cookie `hookflare_session`; `HttpOnly; SameSite=Strict; Path=/api/admin; Secure` (`Secure` omitted only when the request host is `localhost`/`127.0.0.1`).
- Lifetime: idle timeout 12 h, absolute 7 days. `last_seen_at`/`expires_at` are bumped at most once per 5 minutes to limit D1 writes.
- Auth middleware (replaces `accessMiddleware`): read cookie → hash → one query joining `sessions` and `users`; missing/expired session, disabled user, or no password → `401 unauthorized`. The `users` row is still read on every request, so disabling or demoting a user takes effect immediately.
- `POST /api/admin/v1/auth/logout` deletes the session row and clears the cookie.
- Expired sessions are deleted by the existing per-minute job (bounded batch).
- Session creation/deletion is not audited. Login success and failure are Worker log lines only (`admin.login_ok`, `admin.login_failed` with username and reason, never the password), never `audit_logs` rows, so unauthenticated requests cannot write to D1 (my call).

### 6.5 Brute-force and CSRF protection

- New rate-limit binding `LOGIN_LIMITER` (`simple`, 10 requests / 60 s), keyed by `ip:<cf-connecting-ip>` only, checked on every login/setup attempt. Over limit → `429 too_many_attempts`. No per-username key: it would let anyone lock the admin out by guessing wrong on purpose, and Turnstile already covers distributed guessing (my call).
- CSRF: `SameSite=Strict` cookie, plus every non-GET admin request authenticated by cookie (and the public auth endpoints) must have an `Origin` header equal to the request origin (else `403 bad_origin`). Requests authenticated by a Bearer API token (§6.9) skip this check: no browser sends them implicitly.

#### 6.5.1 Turnstile

- **Configuration:** `TURNSTILE_SITE_KEY` (var, public) and `TURNSTILE_SECRET_KEY` (secret). Both set → Turnstile is enforced on `POST /auth/login` and `POST /auth/setup`. Neither set → disabled; the login and setup pages show a visible "Turnstile is off" notice, and `/healthz` reports it (`turnstile: "off"`) without failing. Only one set → both endpoints fail closed with `500 internal_error` and log `admin.turnstile_misconfigured`. (My call: optional so a first deploy still works with zero setup; never half-on.)
- **Client:** `GET /auth/state` also returns `turnstile_site_key` (string or `null`). The pages load `https://challenges.cloudflare.com/turnstile/v0/api.js`, render the widget explicitly with `action` = `login` or `setup`, disable submit until a token exists, send it as `turnstile_token`, and call `turnstile.reset(widgetId)` after every failed submit (tokens are single-use, valid 5 minutes). If the dashboard serves a CSP, it must allow `challenges.cloudflare.com` for script and frame.
- **Server:** order per attempt is: `Origin` check → `LOGIN_LIMITER` → Turnstile → setup token / password hash. Turnstile is checked before PBKDF2 so bots never cost CPU. Validation calls `POST https://challenges.cloudflare.com/turnstile/v0/siteverify` through the `Deps` `fetch` with `secret`, `response`, `remoteip` (`CF-Connecting-IP`), a 10 s timeout, and rejects unless `success === true`, `action` matches the endpoint, and `hostname` equals the request hostname. Missing/oversized (> 2048 chars) token or failed check → `403 turnstile_failed`. Siteverify unreachable, timeout, or non-2xx → `503 turnstile_unavailable` (fail closed; never skip).
- **Local dev and tests:** `.dev.vars.example` ships Cloudflare's always-pass test keys (`1x00000000000000000000AA` / `1x0000000000000000000000000000000AA`); Playwright e2e uses them; unit tests stub siteverify via `Deps.fetch`. Hostname check is skipped only for the test secret key.
- **Setup:** README and `docs/runbook/setup.md` describe creating a widget (Cloudflare dashboard, or the Cloudflare API MCP `POST /accounts/{id}/challenges/widgets` with the Worker hostname as domain, mode `managed`) and setting the two values.

### 6.6 Account management

- `POST /users` takes `{ username, role, password, reason? }` (admin sets the initial password and hands it over out of band).
- `POST /users/:username/password` `{ password, reason? }` (admin, `users.manage`) resets another user's password, deletes all their sessions, and revokes all their API tokens (a reset assumes compromise); audited as `user.password_reset` (no hash in the diff).
- `POST /me/password` `{ current_password, new_password }` (any logged-in user) changes their own password, deletes their other sessions; audited as `user.password_changed`. API tokens survive a self-change (automation keeps working); revoke them explicitly if the account was compromised.
- Disabling a user deletes their sessions in the same batch.
- Existing `PATCH /users/:username` (role, disabled) keeps the last-admin guard, keyed by username; only an admin with a password counts, so a migrated password-less admin cannot mask a lockout.

### 6.9 API tokens (machine access)

Turnstile makes the login form unusable for scripts, so automation uses tokens. (My call; replaces Access service tokens.)

- `api_tokens` table: `id` (prefixed ID), `token_hash` (SHA-256 hex, unique), `username` → `users` ON DELETE CASCADE, `name`, `created_at`, `expires_at` (nullable), `last_used_at` (bumped at most every 5 min), `revoked_at`.
- Token format `hf_<32 random bytes base64url>`, sent as `Authorization: Bearer …`. Shown once at creation.
- A token acts as its user: same role, same per-request `users` read; a disabled user's tokens stop working immediately.
- Admins (`users.manage`) create, list (never the secret), and revoke tokens for any user from Settings › Users; audited as `api_token.created` / `api_token.revoked`.
- The auth middleware accepts either a session cookie or a Bearer token; a request carrying both is rejected (`400`).

### 6.7 Dashboard

- New public routes `/setup` and `/login`. The root loader calls `GET /auth/state`: setup required → `/setup` (and `/login` redirects there); otherwise a `401` from `/me` → `/login?next=<path>`. `/setup` redirects to `/login` once setup is closed.
- Setup page: username, password, confirm password, setup token. Login page: username, password. Both show `429` and `invalid_credentials` as inline errors.
- App shell user menu: shows username and role, "Change password" dialog, "Log out".
- Any `401` from the API (session expired) sends the user to `/login?next=…`; the Access-redirect handling in `lib/api.ts` (`redirected`/`text/html`) is removed.
- Settings › Users: create form gains a password field; row action "Reset password"; email column becomes username.

### 6.8 Removed configuration

`ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `BOOTSTRAP_ADMIN_EMAILS`, `ACCESS_DEV_EMAIL`, the `jose` dependency, `isServiceIdentity`/`SERVICE_IDENTITY_PATTERN`, and `user.bootstrapped`. Added: `SETUP_TOKEN` secret (§6.3), `TURNSTILE_SITE_KEY` var and `TURNSTILE_SECRET_KEY` secret (§6.5.1), and the `LOGIN_LIMITER` binding. Local dev runs onboarding against local D1 like production (`SETUP_TOKEN` in `.dev.vars`).

## 7. Compatibility and release

- Breaking for anyone running 1.0.0 behind Access (config vars removed, identity becomes username, API field renames). Release as **2.0.0** with an upgrade note in `CHANGELOG.md`. (My call.)
- Roadmap: record the deviation from DEC-5/§6.1 in roadmap §3, and update CLAUDE.md invariants ("users row is read on every admin request" stays; Access mentions go).

## 8. Smoke, bench, e2e

- First deploy (and Workers Builds, already configured so) runs with `--skip-smoke`: no account or token exists yet. After onboarding the operator creates a smoke user and token; later deploys run the smoke. `deploy.mjs` keeps refusing to start without smoke env unless `--skip-smoke` (unchanged behavior).
- `scripts/lib/smoke.mjs` and `tools/bench`: replace `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` with `HOOKFLARE_API_TOKEN` (Bearer). The deploy script's missing-env message changes accordingly. The smoke user's role is the lowest one that covers the routes the smoke calls (builder checks).
- Playwright e2e: performs onboarding on a fresh local D1 with the always-pass Turnstile test keys, then logs out and in.

## 10. Testing (minimum)

- Password hash round-trip, wrong password, malformed stored hash, iteration count read from the string.
- Setup: required/closed state, wrong/missing `SETUP_TOKEN`, two concurrent setups → exactly one wins, migrated password-less users still trigger setup.
- Login: success sets cookie flags; every failure kind returns the identical `401`; rate limit per IP (no per-username key).
- Middleware: no cookie, unknown token, idle-expired, absolute-expired, disabled user, demoted user takes effect immediately, `Origin` check on non-GET.
- Turnstile: enforced when both keys set, disabled when neither, `500` when only one; wrong action, wrong hostname, reused/expired token → `403`; siteverify timeout/5xx → `503`; Turnstile is checked before the password hash runs.
- API tokens: Bearer auth works and carries the user's role; revoked, expired, or disabled-user tokens → `401`; cookie + Bearer together → `400`; the secret is never returned after creation.
- Password reset/change revoke sessions; an admin reset also revokes API tokens; disable revokes sessions; audit rows written in the same batch and never contain hashes.
- Migration: an existing 1.0.0 database with users and audit logs migrates losslessly.
- Dashboard: setup/login/redirect flows, change-password dialog, users tab.
