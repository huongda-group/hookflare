# Hookflare — Roadmap & Architecture Baseline

> This is the umbrella document. It records the locked architecture decisions and breaks the roadmap into milestones.
> Each milestone gets its own detailed spec: `docs/superpowers/specs/YYYY-MM-DD-mN-<topic>-design.md`.
> Original requirements: [`DESIGN.md`](../../../DESIGN.md). Where this document differs from `DESIGN.md`, this document wins (see §3).

## 1. Goal

An internal, multi-project inbound webhook gateway that runs 100% on Cloudflare managed services. It receives a webhook and stores it durably before returning `202`. It then delivers the webhook to the backend at-least-once, with automatic retries, a DLQ, a reconciler, replay, an audit log, and an admin dashboard. Guiding principle: **reliability first; do not add components that only add complexity.**

This roadmap covers features and their dependency order only. It does not cover staffing or timelines.

## 2. Locked decisions

| # | Topic | Decision |
|---|---|---|
| DEC-1 | Environments | Each deployment is **a single environment**. For staging and production, deploy several Workers, each with its own D1/R2/Queues. There is no `environment` column or filter. |
| DEC-2 | Traffic | Unknown, so the design targets the medium tier (~50k–1M events/day, peaks of ~50–100 req/s). The overview reads from a rollup table, cleanup runs in batches, and there is a benchmark milestone. |
| DEC-3 | Source auth | Generic only: `none`, `hmac` (configurable header, algorithm, encoding, and prefix), and `token` (header or query). The provider event ID comes from a header or a JSON path. Verifiers are pluggable; provider presets are in the backlog. |
| DEC-4 | Outbound signing | [Standard Webhooks](https://www.standardwebhooks.com/) (`webhook-id`, `webhook-timestamp`, `webhook-signature`). Per-destination secret with dual-secret support during rotation. `X-Webhook-Event-ID` is also sent. |
| DEC-5 | RBAC | A `users` table in D1, keyed by the email from the Access JWT. The first admin comes from `BOOTSTRAP_ADMIN_EMAILS`. Deny by default. Roles are **global** (Admin / Operator / Viewer). |
| DEC-6 | Alerting | A generic outbound webhook (works with Slack/Discord/Google Chat incoming webhooks), plus display on the dashboard. One incident per (rule, resource) pair, with cooldown and auto-resolve. |
| DEC-7 | Topology | **A single Worker** with a `fetch` handler (ingress, admin API, dashboard static assets), a `queue` handler (main + DLQ), and a `scheduled` handler (jobs). Strict module boundaries keep it possible to split ingress into its own Worker later. |
| DEC-8 | Stack | pnpm monorepo: `apps/gateway` (Hono), `apps/dashboard` (React + Vite + Tailwind + TanStack Router/Query), `packages/shared` (types, zod schemas). Data access uses Drizzle ORM; migrations are generated by `drizzle-kit` and applied by `wrangler d1 migrations apply`. Tests use Vitest + `@cloudflare/vitest-plugin`. |
| DEC-9 | SSRF | `https` only. Block IP literals, `localhost`, `*.internal`, and metadata hosts. Resolve DNS over DoH to block private/loopback/link-local/CGNAT/IPv6 ULA ranges, both when a destination is saved **and** before every delivery. Use `redirect: "manual"`. |
| DEC-10 | Pause | Deliveries to a paused destination are held in D1 with status `paused` and do not consume attempts. Resume re-enqueues them in batches. |
| DEC-11 | Per-destination policy | Each destination has its own policy (timeout, max attempts, backoff, max in-flight, rate limit), editable in the UI. All destinations share one statically configured queue. Concurrency and rate limits use one Durable Object per destination. |
| DEC-12 | Archival | Data older than `hot_retention_days` is archived to R2 as one set of files per day, then deleted from D1. The archive is **cold storage**: it can be listed and downloaded, not searched or replayed. |

## 4. Architecture

```text
                     ┌───────────────────────── hookflare Worker ─────────────────────────┐
Provider ──POST /in/:sourceId──▶ fetch: ingress ──▶ D1 (ledger) ──▶ Queue "deliveries"   │
                     │                       └──▶ R2 (payload > 64 KB)       │            │
                     │                                                       ▼            │
                     │   queue: consumer ──▶ DO DestinationLimiter ──▶ fetch backend      │
                     │        │   └──▶ D1 (attempts, status)                              │
                     │        └── DLQ "deliveries-dlq" ──▶ queue: dlq consumer ──▶ dead   │
                     │                                                                    │
Browser ──Access──▶ fetch: /api/admin/v1/* (Hono, RBAC) ──▶ D1 / R2                       │
                     │   fetch: /* static assets (dashboard)                              │
                     │                                                                    │
                     │   scheduled: reconcile · alerts · rollup · archive/retention       │
                     └────────────────────────────────────────────────────────────────────┘
```

Modules in `apps/gateway/src`: `core/` (domain, D1 repositories, crypto, policy), `ingress/`, `delivery/`, `admin/`, `jobs/`. `ingress/` must not import from `admin/`.

## 5. Data model (D1)

IDs are ULIDs with a prefix (`prj_`, `src_`, `dst_`, `evt_`, `dlv_`, `att_`). They sort by time and double as pagination cursors. Timestamps are stored as epoch milliseconds (`INTEGER`). Secrets are encrypted with AES-GCM using a key from the Worker Secret `SECRETS_KEY`.

| Table | Main columns |
|---|---|
| `projects` | id, name, slug, status (`active`/`disabled`), created_at, updated_at |
| `destinations` | id, project_id, name, url, status (`active`/`paused`/`disabled`), signing_secret_enc, signing_secret_next_enc, timeout_ms, max_attempts, backoff_base_s, backoff_max_s, max_in_flight, rate_limit_per_s (a NULL policy field falls back to the global default) |
| `sources` | id, project_id, destination_id, name, status, auth_type, auth_config (JSON), secret_enc, event_id_from (`none`/`header`/`json_path`), event_id_selector, max_body_bytes |
| `webhook_events` | id, project_id, source_id, provider_event_id, received_at, headers_json (redacted), content_type, size_bytes, payload_sha256, body_inline (BLOB ≤ 64 KB) or r2_key |
| `deliveries` | id, event_id, destination_id, project_id, kind (`initial`/`replay`/`test`), status, attempt_count, next_attempt_at, lease_until, enqueued_at, last_http_status, last_error, completed_at, created_by, created_at |
| `delivery_attempts` | id, delivery_id, attempt_no, started_at, duration_ms, http_status, error_kind, error_message, response_snippet (≤ 2 KB) |
| `stats_hourly` | hour, project_id, source_id, destination_id, received, delivered, failed_final, dead, attempts |
| `archive_days` | day, status (`running`/`verified`/`purged`/`failed`), part_count, event_count, bytes, archived_at |
| `users` | email, role, created_at, disabled_at |
| `audit_logs` | id, actor_email, action, resource_type, resource_id, reason, diff_json (redacted), at |
| `alerts` | id, rule, resource_type, resource_id, status (`open`/`resolved`), opened_at, last_notified_at, resolved_at, details |
| `settings` | key, value_json |

Constraints and indexes:
- `UNIQUE(source_id, provider_event_id) WHERE provider_event_id IS NOT NULL`.
- FKs: `webhook_events.source_id → sources.id`, `deliveries.event_id → webhook_events.id`, `deliveries.destination_id → destinations.id`, `delivery_attempts.delivery_id → deliveries.id`.
- Indexes: `deliveries(status, next_attempt_at)`, `deliveries(status, enqueued_at)`, `deliveries(destination_id, created_at)`, `webhook_events(project_id, received_at)`, `webhook_events(source_id, received_at)`, `delivery_attempts(delivery_id, attempt_no)`.

Tables after `settings` are not `STRICT` (drizzle-kit cannot emit it); enums are enforced with `CHECK` constraints instead. `deliveries(event_id)` is indexed for event detail lookups.

M2 notes: `webhook_events.body_inline` stays `NOT NULL` (a zero-length blob when the payload lives in R2; see the M2 spec §3.1 M2-3), and `destinations.backoff_max_s` is capped at 43200 s, the Queues `delaySeconds` maximum (M2 spec §3.1 M2-5).

## 6. Delivery state machine

```text
pending ──enqueue OK──▶ queued ──lease──▶ in_flight
   ▲                                        │
   │ Resume                ┌────────────────┼──────────────────┬───────────────┐
paused ◀── dest paused ────┘                ▼                  ▼               ▼
                                        delivered        retrying ──▶ …   failed_final
                                        (2xx)            (408/429/5xx/    (3xx, other 4xx,
                                                          network/timeout) ssrf_blocked,
                                                              │            payload_missing,
                                                              ▼            destination_disabled)
                                                   attempt_count ≥ max_attempts ──▶ dead
```

- **Terminal states:** `delivered`, `failed_final`, `dead`.
- **Lease:** `UPDATE deliveries SET status='in_flight', lease_until=:now+timeout+30s WHERE id=:id AND (status IN ('pending','queued','retrying') OR (status='in_flight' AND lease_until < :now))`. If no row is affected, the message is a duplicate or the delivery is already terminal: `ack()` and skip.
- **Backoff:** `min(base · 2^(n-1), max)` with ±20% jitter. For 429, `Retry-After` takes priority (capped at `backoff_max_s`). The defaults of 30s / 6h / 20 attempts give a total retry window of about 68h, which meets the 48h recovery requirement.
- **Attempts** count only when the gateway actually sends an HTTP request to the backend. Infra errors (D1/R2), limiter rejections, and paused destinations never count.

## 7. Main flows

### 7.1 Ingress `POST /in/:sourceId`

1. Load source + destination + project (cached in the isolate, 30s TTL). Missing or disabled → `404`.
2. Rate limit per `source_id` (Workers Rate Limiting binding) → `429`.
3. Check `Content-Length` and read the body with a cap (`max_body_bytes`, default 1 MB) → `413`.
4. Verify the signature/token on the raw bytes with a constant-time comparison → `401`.
5. Extract `provider_event_id` (JSON is parsed only **after** verification). Already exists → `200 {duplicate: true, event_id}`.
6. Compute `sha256`. Body > 64 KB → `R2.put(events/YYYY/MM/DD/<evt_id>)`; on failure → `503`.
7. D1 batch (transactional): insert into `webhook_events` (`ON CONFLICT DO NOTHING`) + insert into `deliveries` (`pending`, or `paused` if the destination is paused). On failure → `503`. A concurrent duplicate makes the FK fail → rollback → respond as in step 5.
8. If not paused: `QUEUE.send({deliveryId})`. On failure → `503` (the event is stored; the reconciler will enqueue it).
9. Best-effort `UPDATE … SET status='queued', enqueued_at=:now WHERE id=:id AND status='pending'`.
10. `202 {event_id}`.

Header denylist (applies both to storage and to forwarding): `authorization`, `cookie`, `proxy-*`, `x-api-key`, the source's configured signature/token header, hop-by-hop headers, `cf-*`.

### 7.2 Delivery consumer

Queue `deliveries` uses global settings: `max_batch_size=10`, `max_concurrency` tuned after benchmarking, a high `max_retries` as a safety net, and DLQ `deliveries-dlq`. Messages in a batch are processed in parallel, and each one is acked or retried on its own.

1. Load delivery + event + destination; acquire the lease (§6).
2. Destination `paused` → `paused`, ack. `disabled` → `failed_final`. Payload missing → `failed_final (payload_missing)`.
3. Request a slot from the `DestinationLimiter` DO (`max_in_flight`, `rate_limit_per_s`). Rejected → `msg.retry({delaySeconds: 5–30})`, no attempt counted.
4. Load the payload (inline or R2). R2 error → `msg.retry(60s)`, no attempt counted.
5. SSRF check → blocked: `failed_final (ssrf_blocked)`.
6. Sign with Standard Webhooks; `fetch(url, {redirect: 'manual', signal: AbortSignal.timeout(timeout_ms)})`; release the slot.
7. Classify the result by the Retry Policy → D1 batch: insert attempt + update delivery → `ack()` or `retry({delaySeconds})`.

DLQ consumer: marks the delivery `dead` (if not already terminal), records `last_error`, and opens an alert.

### 7.3 Scheduled jobs

Every job is bounded (a LIMIT per run) and idempotent.

| Schedule | Job | Logic |
|---|---|---|
| `* * * * *` | Reconcile | (a) `pending`, `enqueued_at IS NULL`, created more than 60s ago → enqueue. (b) `in_flight` with a lease expired for 5 minutes → `retrying` + enqueue. (c) `retrying` with `next_attempt_at` overdue by 15 minutes → enqueue. (d) `queued` with `enqueued_at` older than 30 minutes → enqueue. Every enqueue resets `enqueued_at` (cooldown). At most 500 rows per run, using `sendBatch`. |
| `* * * * *` | Alerts | Rules: a destination fails 5 times in a row, a new `dead` delivery appears, a `pending`/`queued` delivery waits more than 5 minutes, D1 nears its storage limit. Opens/resolves incidents and sends the alert webhook with cooldown. |
| `* * * * *` (every 5 minutes) | Rollup | Recomputes `stats_hourly` for the current and previous hour. |
| `0 3 * * *` | Archive & retention | §7.4. |

Resuming a destination: the API moves its `paused` deliveries to `pending` (`enqueued_at = NULL`) in batches and enqueues the first batch right away. Reconcile (a) handles the rest.

### 7.4 Archive & retention

Settings (Admin › Settings › Storage): `archive_enabled` (default on), `hot_retention_days` (30), `failed_retention_days` (90), `archive_retention_days` (empty = keep forever), `audit_retention_days` (365).

1. An event is eligible for archival when **all of its deliveries are terminal** and either:
   - all of them are `delivered` and the event is older than `hot_retention_days`; or
   - at least one is `failed_final`/`dead` and the event is older than `failed_retention_days`.

   An event with any non-terminal delivery (`pending`/`queued`/`in_flight`/`retrying`/`paused`) never leaves D1.
2. For each day D that has eligible events: stream them to `archive/YYYY/MM/DD/part-NNNN.ndjson.gz` (gzip via `CompressionStream`, R2 multipart upload). Each line holds the event, its payload (base64, including payloads that currently live in R2, so the archive is self-contained), its deliveries, and their attempts. Each part holds at most 50,000 events.
3. Write `archive/YYYY/MM/DD/manifest.json` (event count, sha256 of each part, ID range) and update `archive_days`.
4. Verify (HEAD every part, match the counts) → `verified` → delete from D1 in batches (and delete the matching `events/…` objects) → `purged`. If a run fails midway, the next run resumes from the state in `archive_days`.
5. Delete archive days older than `archive_retention_days`. `audit_logs` older than `audit_retention_days` are archived the same way to `archive/audit/YYYY/MM/DD/`.

When `archive_enabled = false`, the job deletes eligible data directly under the same conditions, without writing to R2.

## 8. Admin API, RBAC & Dashboard

- Middleware verifies `Cf-Access-Jwt-Assertion` against the team's JWKS and the `aud` tag (env `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`), then looks up the email in `users`. Missing or disabled → `403`.
- Access protects `/` and `/api/admin/*`; `/in/*` stays public.

| Permission | Viewer | Operator | Admin |
|---|:-:|:-:|:-:|
| View overview, events, attempts, redacted headers | ✓ | ✓ | ✓ |
| View raw payloads, download archives | | ✓ | ✓ |
| Replay (single / bulk ≤ 100, `reason` required), Pause/Resume, Test delivery | | ✓ | ✓ |
| CRUD projects/sources/destinations, rotate secrets, edit delivery policy | | | ✓ |
| Settings, user management | | | ✓ |

- Replay creates a new delivery with `kind=replay` and keeps the existing history. Payload missing → `409`. Every mutation writes to `audit_logs` (with secrets redacted from the diff).
- Test delivery sends a sample payload synchronously (`kind=test`) and returns the result immediately; the attempt is still recorded.
- A secret is shown only once, when it is created or rotated; after that only its fingerprint is shown.
- REST endpoints follow `DESIGN.md` §7, plus: `/api/admin/v1/users`, `/api/admin/v1/archives`, `/api/admin/v1/archives/:day/:part` (download), `/api/admin/v1/alerts`, `POST /api/admin/v1/failures/replay` (bulk), `POST /api/admin/v1/sources/:id/rotate-secret`, `POST /api/admin/v1/destinations/:id/rotate-secret`.
- Dashboard pages: Overview · Projects · Endpoints (source + destination + policy) · Events · Event Detail (timeline) · Failures (Failed Final / Dead Letter) · Archives · Alerts · Audit · Settings (Retry defaults, Storage, Alerts, Users).

## 9. Testing strategy

- **Unit:** auth verifiers, provider event ID extraction, retry classifier, backoff/jitter/`Retry-After`, SSRF guard (IPv4/IPv6, CGNAT, link-local), header denylist/redaction, Standard Webhooks signing, archive eligibility.
- **Integration** (`@cloudflare/vitest-plugin`): real D1, Queues, R2, and Durable Objects in Miniflare; the backend is simulated with a mocked outbound fetch (2xx/3xx/4xx/429/5xx/timeout).
- **Fault injection:** adapters around D1/R2/Queue that can be forced to fail, used to test: 503 when D1/R2/Queue fails, reconciler recovery, a successful send followed by a failed D1 update, duplicate messages, expired leases, and an archive run that fails midway.
- **Smoke test** after every deploy: send a webhook → delivered → replay.
- Every criterion in `DESIGN.md` §11 must map to at least one automated test or one runbook step.

## 10. Roadmap

```text
M0 ─▶ M1 ─▶ M2 ─▶ M3 ─┬─▶ M4 ─┬─▶ M6
                      └─▶ M5 ─┘
```

### M0 — Foundation
- **Scope:** pnpm monorepo; `apps/gateway` (Hono) with a `wrangler.jsonc` holding one environment per deployment; D1 migration tooling; prefixed IDs; AES-GCM secret encryption; logger with redaction; CI (typecheck, lint, test); `@cloudflare/vitest-plugin` setup.
- **Exit:** CI is green; an empty Worker with `/healthz` deploys; migrations run on both local and remote D1.

### M1 — Core pipeline
- **Scope:** schema for `projects`/`sources`/`destinations`/`webhook_events`/`deliveries`/`delivery_attempts`; a minimal API to create projects/sources/destinations (temporarily locked behind Access + bootstrap admin); ingress per §7.1 with inline payloads (≤ 64 KB; larger bodies temporarily return 413); `none`/`hmac`/`token` auth; enqueue; a single-shot consumer (2xx → `delivered`, anything else → `failed_final`); Standard Webhooks signing; SSRF guard; attempt logging.
- **Exit (§11):** the gateway still receives and stores webhooks while the backend is offline; every delivery records HTTP status, latency, and errors.

### M2 — Reliability
- **Scope:** full Retry Policy, backoff + `Retry-After`, lease, retry budget in D1, `dead` + DLQ consumer; idempotency by provider event ID; R2 for payloads > 64 KB; Reconcile job; Pause/Resume; per-destination policy (`timeout_ms`, `max_attempts`, `backoff_*`); fault-injection test suite. Before adding the UNIQUE index on `(source_id, provider_event_id)`, a migration must collapse duplicates stored by M1 (M1 stores provider event IDs without dedup).
- **Exit (§11):** never return 202 before D1/R2/Queue writes complete; a backend that recovers after 48h still receives its webhooks; duplicates do not create new logical events; the reconciler recovers from partial failures; tests exist for D1/Queue failure, timeout, retry, duplicates, and SSRF.

### M3 — Admin API & Security
- **Scope:** Access JWT verification; `users` + RBAC + bootstrap admin; `audit_logs`; full admin API (§8); single and bulk replay; test delivery; secret rotation (source secrets and dual-secret outbound); event search/filtering with cursor pagination.
- **Exit (§11):** the admin API is protected by Access and RBAC; replay works and preserves past history; every replay is audited.

### M4 — Dashboard
- **Scope:** `apps/dashboard` served via Workers Static Assets; Rollup job + `stats_hourly`; every page in §8 except Archives and Alerts; permission-aware JSON viewer; delivery timeline.
- **Exit (§11):** the DLQ is visible on the dashboard; projects/sources/destinations can be created and configured entirely from the UI.

### M5 — Operations
- **Scope:** Alerts job + incidents + alert webhook + Alerts page; Archive & retention per §7.4 + Archives page + Settings › Storage; `DestinationLimiter` Durable Object (`max_in_flight`, `rate_limit_per_s`).
- **Exit:** alerts fire correctly for 5 consecutive failures, new DLQ entries, and pending deliveries older than 5 minutes; archives are verified before deletion and re-runs after failures are safe; the limiter never consumes attempts.

### M6 — Production readiness
- **Scope:** benchmarks (ingress D1 write throughput, consumer concurrency, D1 size as a function of `hot_retention_days`); D1 backup/restore (Time Travel + scheduled exports) and a restore drill; operations runbook; migration and rollback procedures; external uptime monitoring; queue configuration tuning.
- **Exit (§11):** the runbook, migrations, backup/restore, and rollback exist and have been tested; benchmark results and recommended limits are documented.

### M7 — Built-in auth
- **Scope:** username/password login with server-side sessions, one-time onboarding protected by `SETUP_TOKEN`, API tokens, Turnstile on the login/setup forms, smoke/bench via `HOOKFLARE_API_TOKEN`; Access removed.
- **Exit:** a first deploy needs no Zero Trust setup — open the Worker URL, claim the first admin, and use the dashboard; every test in the M7 spec §10 passes.

### Backlog (outside the current roadmap)
Provider presets (Stripe/GitHub/Shopify) with timestamp tolerance; per-project RBAC; restoring an archived day into D1; splitting ingress into its own Worker; the "out of MVP scope" items in `DESIGN.md` §12.

## 11. Risks to watch

| Risk | Impact | Mitigation |
|---|---|---|
| D1 per-database size limit (10 GB) | At 1M events/day, inline payloads could fill D1 within days | Measure real usage in M6; consider a lower inline threshold or shorter `hot_retention_days`; alert when D1 nears its limit |
| D1 single writer | Ingress slows down or fails at peak traffic | Ingress writes only one batch + one update; benchmark in M6 |
| DoH lookup on every delivery | Extra latency and a dependency on the resolver | Cache results for 60s; treat resolver errors as retryable, never as `failed_final` |
| Archiving a large day exceeds cron CPU/time limits | Archival does not finish in one run | Split into parts, track progress in `archive_days`, continue on the next run |
