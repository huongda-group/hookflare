# Destinations and backend protection

[Documentation index](README.md)

## Business rules and current behavior

A destination is an HTTPS backend endpoint belonging to a project. Admins (`config.write`) configure name, URL, timeout, retry overrides, concurrency and rate limits, and rotate the signing secret. Operators (`destinations.operate`) can pause/resume and send test deliveries. Everyone with `events.read` can list and inspect destinations and their stats and test history.

Destination URLs can carry credentials in the path or query, so only actors with `config.write` see them in full. Every other response (list, detail, pause/resume) returns the origin, plus `/…` when anything follows it (for example `https://api.example.com/…`).

URLs are checked on create and on URL change: HTTPS only, no userinfo, no IP literals or internal hostnames, and every resolved A/AAAA address must be public. A blocked URL returns `422 unsafe_url` with a `reason`; a DNS resolver failure returns `503 unavailable`. The same check runs again before every delivery and test; see [delivery](delivery.md).

Status is `active`, `paused`, or `disabled`. `paused` is set only by Pause; PATCH sets `active` or `disabled`.

- **Pause** (`active` → `paused`): new deliveries and those reaching the consumer are held as `paused` without consuming attempts; a request already in flight finishes.
- **Resume** (`paused` → `active`): moves up to 100 of the oldest paused deliveries back to `pending` and enqueues them immediately; the reconciler releases the rest. The response reports `resumed`.
- **Disable**: deliveries reaching the consumer end as `failed_final` (`destination_disabled`) without an attempt, the reconciler fails held paused deliveries the same way, and replay and test delivery are refused. Enable (`PATCH {status: "active"}`) accepts new deliveries again; deliveries that already failed stay failed until replayed from [Failures](replay.md).

Pause and Resume are idempotent: repeating one returns the current destination, and only an actual transition is audited. Pause or Resume on a disabled destination returns `409 conflict` with `reason: "destination_disabled"`. A URL change or a return to `active` resets the destination's consecutive-failure streak used by [alerts](alerts.md).

A test delivery sends the default `{type: "hookflare.test", destination_id, timestamp}` envelope, or a custom JSON `payload`. A custom payload requires `config.write` (`403 {error:"forbidden", required:"config.write"}` otherwise), because it is signed with the real secret and the backend cannot tell it from a real event. Every test request carries the header `x-hookflare-test: 1`, uses a `tst_…` ID as `webhook-id`, and has no `X-Webhook-Event-ID`. A test runs synchronously with the destination's resolved timeout, also against a paused destination, and returns `409 destination_disabled` for a disabled one. An SSRF block is recorded as a test result (`error_kind: ssrf_blocked`) without sending. The `destination.tested` audit entry records the payload's SHA-256 hex (`payload_sha256`), never the payload itself.

The signing secret is `whsec_` followed by base64 of 32 random bytes. It is generated by the gateway and returned only in the create and rotate responses. Rotation takes `grace_hours` 0–168 (default 24); during the grace window both signatures are sent (see [contract](contract.md)), and 0 drops the previous secret immediately. A concurrent rotation returns `409 conflict`.

## Design and interaction

Endpoints → Destinations provides list/detail, policy editing, confirmed pause/resume/disable with an optional reason, test delivery, and secret rotation. API prefix `/api/admin/v1/destinations` includes list/create (`422 invalid_reference` for an unknown `project_id`), GET/PATCH `/:id`, `/stats?range=24h|7d|30d`, `/:id/pause`, `/:id/resume`, `/:id/test`, `/:id/tests` (cursor-paginated history), and `/:id/rotate-secret`.

The Destinations tab lists and creates destinations in the active project. Its detail, actions, stats, and test history keep that project scope. Detail shows configuration, the retry policy, the signing-secret fingerprints with the grace expiry, last-24-hour stats, and test deliveries. The action menu offers Edit, Rotate secret, and Disable (or Enable when disabled, confirmed with an optional reason) to `config.write`, and Pause (when active), Resume (when paused), and Send test to `destinations.operate`. The test dialog accepts a JSON payload up to 64 KB only for `config.write`.

A destination policy field (`timeout_ms` 1,000–30,000, `max_attempts` 1–50, `backoff_base_s` 1–3,600, `backoff_max_s` 1–43,200) overrides the corresponding [retry default](settings.md); an unset (`null`) field inherits. The UI shows inherited values as `default: <value>` rather than a blank or zero. After defaults apply, `backoff_max_s` must be at least `backoff_base_s` (`400`), but only a create or a PATCH that touches backoff fields is validated, so raised defaults never block unrelated edits; the delivery path raises the effective maximum to the base instead.

`max_in_flight` and `rate_limit_per_s` (1–1,000, `null` = unlimited) protect one backend through a per-destination Durable Object limiter. It counts in-flight slots (each expires after the timeout plus 30 seconds if never released) and runs a token bucket with at most one second of burst. A rejected delivery is re-sent after the limiter's hint plus 0–3 seconds of jitter (1–30 seconds) and never consumes an attempt; a limiter that does not answer within 2 seconds is an infrastructure error. Limits are passed on every call, so a change applies to the next delivery.

## Ideas, boundaries, and open work

A destination is not a fan-out workflow. Rate/concurrency limits protect an individual backend; they do not establish measured system throughput.
